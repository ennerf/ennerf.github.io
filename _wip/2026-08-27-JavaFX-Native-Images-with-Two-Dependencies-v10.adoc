We initially used https://www.graalvm.org/native-image/[GraalVM Native Image] as a way to deploy JavaFX to mobile targets. However, after seeing significant performance benefits (GUIs mostly run in interpreted mode since users would have to click thousands of times to reach the JIT threshold), we gradually migrated all of our desktop and CLI applications over to ahead-of-time (AOT) compilation.

JavaFX actually works very well in Native Image once everything is configured, but getting a complex application running for the first time is typically not a straightforward experience. This steep initial hurdle has unfortunately earned JavaFX, and desktop Java in general, a reputation of being incompatible or working poorly with native image.

I think a big part of this stems from complex, specialized tooling that performs a lot of "magic" behind the scenes to hide the native layers. Whenever anything breaks, it produces errors that many Java developers don't know how to debug.

In this post I want to demystify the internals a bit, and show how to run the latest JavaFX 27 release with stock Oracle GraalVM.

== Technical Background

Most native-image adopters use frameworks like https://quarkus.io/[Quarkus] or https://micronaut.io/[Micronaut] that were specifically designed for ahead-of-time compilation, and whose applications usually run on reproducible servers that the engineers control. JavaFX, on the other hand, is a rather large and highly dynamic GUI framework that predates native-image by a decade, and its applications need to run on arbitrary client machines with different operating systems.

Several layers have to work together to make this possible. In general, each solution has to solve three different problems:

1. *Reachability metadata*: Native image uses a closed-world assumption, so every resource, class, and method that gets accessed reflectively at runtime needs to be known at build time (e.g. `reachability-metadata.json`). Note that there are really two separate parts to the metadata, one part for the user's own application, and the other for the underlying JavaFX engine itself.

2. *The static binaries*: Roughly half of JavaFX is C/C++/Objective-C code (windowing, rendering, fonts, image loading, effects). A self-contained executable needs these libraries compiled as static archives, which upstream supports via `-PSTATIC_BUILD=true` but does not publish.

3. *Static integration glue*: A few things work differently under AOT and need to be bridged with glue code. For example, GraalVM's linker requires the JNI symbols of all included classes to be available at link time, even if those code paths could never actually be executed. This is an issue when, e.g., a Windows image wrongly includes a Linux font rendering class that depends on several Linux-only symbols. The resulting missing symbol errors can look cryptic to Java developers and give the impression that the binaries were not compiled correctly.

== Existing Solutions

So far there have been two established solutions to solve this, Gluon's Substrate, and Liberica NIK.

=== Gluon Substrate

Gluon's Substrate is a toolchain that can port JavaFX to just about anything, including iOS, Android, Windows, macOS, Linux, and small 32-bit embedded boards, as an executable, a shared or static library, or an OS-specific installer. Getting the whole matrix to work takes custom builds of GraalVM, the JDK, and JavaFX, additional rendering backends, mobile wrapper applications, and dedicated Maven and Gradle plugins. They have built an impressive stack, and we owe Gluon for contributing a lot of the upstream changes that let JavaFX run everywhere.

However, the number of moving targets makes for a brittle combination that can break at the whims of Apple or Google, e.g., when they raise the minimum version an application has to target. While the tooling is about as user-friendly as it can be, the biggest problem in practice was the application-side metadata: the tracing agent is unreliable for GUI applications, and there was no other way to create the entries. I gave up four times before I eventually got an application deployed on mobile. Once it was there, however, it worked very well: I don't know of any other framework that can deploy to all five targets with full 2D and 3D rendering and hot-reload of styling and layouts on several devices at once.

Gluon has come to a similar conclusion about the maintenance burden and is moving its mobile support away from GraalVM towards https://gluonhq.com/news/bringing-openjdk-to-mobile-a-community-effort/[OpenJDK Mobile]: in their words, "every new release of iOS, Android, the AOT compiler, the JVM components or the JDK required patches and adjustments", and that approach does not scale. It likely also helps that a real JVM like Zero has no closed-world assumption, so the metadata problem disappears entirely.

The Substrate stack is still active, but its default versions have fallen behind: a GraalVM 23 CE build from late 2024, a JDK 18 early-access static JDK, and a 21-ea JavaFX. That rules out everything that came after, e.g., platform preferences, `RichTextArea`, custom titlebars, and the https://mail.openjdk.org/pipermail/openjfx-dev/2025-June/054648.html[Headless platform], and the versions seem unlikely to see major updates now that the focus has shifted. The embedded landscape has also moved on: boards like the Raspberry Pi now run full aarch64 Linux distributions, and JavaFX 26 removed the Monocle glass backend that Gluon's Raspberry Pi support was built on.

=== Liberica NIK

https://bell-sw.com/liberica-native-image-kit/[Liberica NIK] took the opposite approach and focused purely on desktop applications. BellSoft's answer to all three problems is a single per-OS bundle: the "full" distribution is a GraalVM that contains the JavaFX modules, the matching static archives, and the glue, so there is exactly one JavaFX in the picture and stock native-image builds a JavaFX application with zero changes. Users only have to deal with the application-side metadata, e.g., BellSoft's own https://bell-sw.com/blog/how-to-create-javafx-native-images/[tutorial] walks through collecting it with the tracing agent, but this makes NIK by far the easiest way to get started.

It is also the only route that supports AWT and Swing in native images. Swing and AWT are part of the JDK itself, so their static libraries and support code can realistically only ship inside a JDK distribution. JavaFX being decoupled from the JDK, on the other hand, is what allows anyone to provide the same integration as plain dependencies, without waiting for a vendor.

The limits are the release cycle (currently GraalVM 25 with JavaFX 25, coupled on BellSoft's cadence), the community edition of GraalVM (weaker escape analysis, no G1 GC, no PGO), and the supported operating systems (no linux-aarch64, no mobile).

== A Third Option

For context, I've been using Liberica NIK for our desktop applications for about two years, and it has admittedly worked quite well. My main issue is that some of our tools actively measure https://ennerf.github.io/2016/09/20/A-Practical-Look-at-Latency-in-Robotics-The-Importance-of-Metrics-and-Operating-Systems.html[latency] at the sub-millisecond level, so even minor GC pauses in the GUI show up as incorrect measurements. A lot of code in the JDK is written with the assumption that escape analysis removes non-escaping allocations, but the community edition that both Gluon and BellSoft build on has a significantly weaker implementation than Oracle GraalVM. One of my worst GC causes eventually turned out to be `Math::pow`, which would never allocate on HotSpot. Since Oracle GraalVM became free to use under the https://www.oracle.com/downloads/licenses/graal-free-license.html[GFTC] license in 2023, I wanted to move to it for the G1 GC, the better escape analysis, and features like PGO. I also wanted the latest JavaFX for the Headless platform and for linux-aarch64 targets like the Raspberry Pi. Neither of the existing routes covers this combination.

That is how this work became a third option, with its own set of trade-offs. It is arguably less convenient than NIK and supports neither mobile targets nor JavaFX versions before 26. In exchange, the JavaFX and GraalVM versions are decoupled, i.e., it works with any GraalVM 25+ and follows upstream JavaFX releases directly. The answers to the three problems live in the published artifacts themselves rather than in a build tool or a patched VM:

== Application Metadata

The application side is where most user problems come from, so it is covered first.
// * GraalVM provides an automated https://www.graalvm.org/latest/reference-manual/native-image/metadata/AutomaticMetadataCollection/[tracing agent], but it's difficult to use for JavaFX as a developer would have to click through every feature on every supported operating system, and redo it every time the app changes.

The application's own metadata deserves its own section before getting to the engine, because it is usually the first obstacle to adoption and the one that gave JavaFX most of its bad reputation. FXML resolves controllers, imported types, and `@FXML` members through reflection, so every view adds a set of entries that need to be maintained by hand or traced by the agent.

This part is handled by an annotation processor, https://github.com/HebiRobotics/reachability-annotations[reachability-annotations], that parses the FXML and CSS files at compile time and generates the metadata for everything they reference:

[source,java]
----
@ReachableFxResources({
        "/assets/images/*.png",   // relative to classpath root
        "views/**/*.fxml",        // relative to the annotated type
        "views/**/*.css",
})
public class MyApp extends Application {}
----

The processor walks the matched files and emits reflection entries for the referenced controllers and imported classes, as well as resource entries for the files themselves and anything they include. All entries are conditioned on the annotated class, so unused views do not increase the image size. Since the metadata is regenerated on every compile, it cannot get out of sync with the views it describes.

Note that this project has nothing to do with static linking and works with any native-image build, i.e., it is the same on Liberica NIK or Gluon. It is also the only piece the application has to contribute. Everything from here on is about the engine side, which the two dependencies cover.

== Engine Metadata

The engine's own metadata is where the three routes differ the most. It is also the one problem the tracing agent is structurally unable to solve. Some entries depend on the operating system: the DirectWrite font backend must be registered on Windows, but must not be registered on Linux, where its reachable native methods fail the link with 65 unresolved symbols. A flat list recorded on one machine cannot express that condition. Other entries cover generated code: the shaders and effect peers are generated families of classes and resources, and the agent records only the shaders that one particular run happened to compile. The entries need to be conditional, and the agent has no way to produce conditions.

Gluon's metadata is JSON. Substrate concatenates its own bundled configs with any `META-INF/substrate/config/reflectionconfig.json` it finds in the class-path jars, and per-OS variants use separately named files, e.g., `reflectionconfig-${archOs}.json`. The mechanism works, but only Substrate reads these locations. The software rendering pipeline is opt-in the same way, i.e., a `usePrismSW` flag adds the `-javafxsw` config files.

NIK ships no JSON at all, which surprised me. Decompiling the `svm.jar` of NIK 25.0.3 shows a heavily extended `com.oracle.svm.hosted.javafx` package: the metadata is hand-written registration code compiled into their patched native-image, guarded by per-OS `Platform.includedIn` checks and by trigger classes like `javafx.fxml.FXMLLoader`. That is conditional metadata expressed as code. However, the knowledge is tied to the bundled JavaFX version and invisible outside NIK, and some coverage choices are baked in. For example, the registrations for the software pipeline exist in the code but are never called, so `-Dprism.order=sw` is not available on a NIK image.

The metadata that ships with `jfx-static-libs` is generated from the source instead. `@Reachable` annotations sit in the JavaFX sources next to each reflective lookup and are compiled into the jars by the regular build, so the entries are reviewable in a diff and versioned together with the code they describe. Platform-specific entries are conditioned on classes that only exist in that platform's code path, which lets a single metadata set serve all five platforms. Generated classes carry their annotations in the templates that generate them, e.g., a single annotation in the shader template covers all 212 generated shader loaders. Since the coverage describes the full engine rather than what a run happened to touch, the software pipeline works in every image. The annotation pass came to roughly 800 added lines across a bit under 200 files, which generate about 790 conditional entries and cost about 0.2% of the image size on GraalVM 25.3.

The same knowledge exists in all three routes, so the practical difference is where it lives. Metadata inside the jar moves with the JavaFX version, needs no special tooling, and works the same on any GraalVM.

Missing metadata does not fail at build time. It fails at runtime, and sometimes silently, so each release is verified by a rendering check: a headless example draws a fixed scene covering 2D, 3D, effects, dialogs, popups, and rich text, checks its own pixels, and runs on every commit on all five platforms. Beyond the synthetic scenes, the AtlantaFX sampler from the opening picture and https://www.youtube.com/watch?v=E9csKYFPwaM[Scope], our diagnostics GUI at https://hebirobotics.com/[HEBI Robotics], run as native images on real GPUs across the supported platforms. Something may still have been missed, in which case the metadata can be respun as a `${javafx.version}-1` patch release without touching the JavaFX build itself. The most instructive failure so far is described in the appendix.

There is a lot more to say about this topic, e.g., which reflective lookups native-image constant-folds on its own, and a limitation in the current metadata schema that cannot express a per-OS choice once a platform-independent class like the headless toolkit is involved. I'm planning to cover the details in a separate post.

== The Static Libraries

The static binaries are the most mechanical problem. Upstream OpenJFX has supported static builds via `-PSTATIC_BUILD=true` for years, but has never published the resulting archives, so everyone who wanted them had to either build them or take a vendor's patched version.

The two vendors solve this in opposite ways. Substrate downloads Gluon's own static JavaFX SDK for the configured `javafxStaticSdkVersion`, a per-target zip that contains both the jars and the archives, and before it invokes native-image it rewrites the class path: every `javafx-base`, `javafx-graphics`, `javafx-controls`, `javafx-fxml`, `javafx-media`, and `javafx-web` entry is replaced by the corresponding jar from that SDK (see `processClassPath` in `AbstractTargetConfiguration`). That guarantees matching jars and archives, but it means that the JavaFX the user compiles and tests against on the JVM is not necessarily the JavaFX that ends up in the image, and the version has to be one that Gluon has published. BellSoft removes the choice entirely: NIK bundles the JavaFX modules and the matching static archives inside the JDK, so there is exactly one JavaFX in the picture, on BellSoft's release cadence.

Here, the archives come from upstream. https://github.com/ennerf/jfx[ennerf/jfx] is a fork of `openjdk/jfx` at the release tag that adds the reachability annotations and a CI workflow. There are no functional changes to the JavaFX code, i.e., the annotations only add metadata to the jars, and the fork is two commits per release. For each release, CI builds the static SDK for `windows-x86_64`, `linux-x86_64`, `linux-aarch64`, `darwin-x86_64`, and `darwin-aarch64`. Note that the Linux builds run on the oldest supported Ubuntu LTS, because the build host's headers determine the oldest glibc the archives can link against.

`jfx-static-libs` packages every platform's archives together with the metadata into a single jar of roughly 10 MB, without any classifier. Packaging all platforms into one artifact removes the need for OS detection, Maven profiles, and per-platform classifiers, and Maven and Gradle resolve it identically. The archives of the other platforms only cost a one-time download, since no resource configuration references them and they never enter an image.

One constraint that dynamic linking hides is that the Java classes and the native archives have to come from the same JavaFX build. The JNI side of JavaFX is not a stable interface, and a mismatch shows up as an undefined symbol at link time. Gluon guarantees the match by swapping the class-path jars for its own, and NIK by bundling exactly one JavaFX. Here, `jfx-static-libs` is versioned by the JavaFX release it was built from and declared with the same `${javafx.version}` property as the `org.openjfx` jars. If the versions still disagree, e.g., due to a stale pin in a parent pom, the feature aborts the build with a message that names both, rather than failing later with a linker error. The feature itself has its own version line, since the substitutions have not had to follow a JavaFX change in years.

== Static JNI Integration

Linking the archives into an image is the last problem: something has to tell native-image that the JavaFX native code is compiled into the image rather than loaded from shared libraries, and work around the places where GraalVM and a statically linked JavaFX do not fit together yet. Both vendors handle this in the only places available to them — Substrate as code inside the build tool, BellSoft as patches inside its native-image — and neither can be reused outside its own stack.

Here it is handled by `jfx-static-feature`, a GraalVM https://www.graalvm.org/sdk/javadoc/org/graalvm/nativeimage/hosted/Feature.html[Feature] that is picked up from the class path by any stock native-image. It registers the JNI package prefixes as builtin, adds the platform's archives as static JNI libraries, and names the system libraries they reference, i.e., GTK on Linux and the Cocoa frameworks on macOS, which stay dynamic (see Trade-offs). Doing this in a feature keeps the list out of every consumer's build without patching anything.

=== Removing the Need for C Stubs

GraalVM's analysis keeps the font and image backends of the other platforms reachable. For example, when building on Windows, the Linux freetype code and the macOS CoreText code are still on the class path and still reachable, but the Windows archives contain none of their native methods, and every unresolved native method in a static JNI library is a link error. This is the platform problem from the metadata section showing up one level lower: even perfectly conditional metadata cannot remove classes that the analysis reaches on its own. The obvious fix is a small C stub for each missing function, which in this case would have been around 45 stubs per platform.

I wanted to avoid this, because it would reintroduce a significant practical problem: custom C code has to be compiled on every platform with a matching toolchain, and the resulting object files have to be added to the native-image link. A feature could theoretically automate that, but the stub archive would have to match the JavaFX version exactly, so it would only really be safe if the stubs were generated inside the JavaFX build itself.

Instead, the feature uses GraalVM's `@Delete` substitution to remove those classes from the analysis entirely, so their native methods are never reachable and never need to resolve. This is plain Java, independent of the JavaFX version, and requires no toolchain beyond what native-image already needs. The conditions are negations (`NotLinux`, `NotMacOS`) rather than inclusion lists, so a future iOS or Android port would fail visibly instead of silently keeping a stubbed-out backend.

Beyond the deletions, the feature contains a small number of substitutions that work around remaining gaps between GraalVM and a statically linked JavaFX, e.g., calling the `JNI_OnLoad` initializers directly and pumping a Cocoa run loop on the first thread on macOS. The appendix lists them individually.

== Trade-offs

There are a few limitations that are worth being clear about:

* *System libraries.* The image contains all of the JavaFX native code, but GTK on Linux and the Cocoa frameworks on macOS are dynamic dependencies, the same as for any native application. Any machine that can run GTK applications has everything the image needs.
* *Raspberry Pi.* JavaFX qualifies GPUs using a vendor allowlist that predates the Pi's Mesa V3D driver, so the es2 pipeline requires `-Dprism.forceGPU=true` and otherwise falls back to software rendering. The upstream fix is a one-line addition to the allowlist.

== Getting Started

The entire engine-side integration consists of two dependencies in addition to the ordinary `org.openjfx` jars:

[source,xml]
----
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-feature</artifactId>
    <version>1.0</version>
</dependency>
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-libs</artifactId>
    <version>${javafx.version}</version>
    <scope>runtime</scope>
</dependency>
----

There are no other requirements: no `--add-exports` flags or linker options, no platform classifiers or OS-specific profiles, and no JSON configuration files for JavaFX. The https://github.com/ennerf/jfx-static-feature[jfx-static-feature] repository contains a complete `example-hellofx` module whose parent pom is the entire recipe. With a GraalVM 25 in `JAVA_HOME` and the platform's C toolchain available, the following command produces a self-contained executable:

[source,shell]
----
mvn -Pnative package -pl jfx-static-examples/example-hellofx -am
----

On Windows, the result runs from an empty directory with no DLLs next to it.

If you are not ready for static linking, `jfx-static-libs` is useful on its own: the metadata sits in the standard `META-INF/native-image/` location, so adding the jar to a regular dynamically linked JavaFX native image provides the entries that the Maven Central `org.openjfx` jars are missing, without using the feature or the static libraries at all. Combined with `@ReachableFxResources` for the application side, this replaces the tracing agent entirely, which in my experience is where most of the day-to-day friction comes from.

== Appendix: The Remaining Glue

This section collects the individual workarounds inside `jfx-static-feature` for readers who run into the corresponding errors, or who want to fix the underlying issues. None of them are application specific, and most of them belong upstream, either in GraalVM or in OpenJFX:

* `System.loadLibrary` cannot load any of the static JavaFX libraries. On Windows, glass reports JNI version 1.2 from its `JNI_OnLoad`, while the spec requires 1.8 or later for statically linked libraries (an upstream bug with a one-line fix). On Linux and macOS, the `JNI_OnLoad_<lib>` symbols are hidden by the image's linker version script. The feature calls the initializers directly.
* Overloaded native methods never link, because Substrate resolves builtin JNI methods by their short name, and an overloaded native only exists under its signature-mangled name on the C side. The four `directwrite.OS` overloads on Windows, and `MacTimer._start` and `coretext.OS.CFStringCreateWithCharacters` on macOS, are routed to the mangled symbols via `@CFunction` substitutions.
* On macOS, the process hangs before the first window appears. Cocoa requires the first thread of the process to be pumping a run loop while glass starts up. The `java` launcher arranges this, but a native image runs `main` on the first thread. This has been known since https://github.com/oracle/graal/issues/994[2019], and the common answer has been an external Objective-C launcher. GraalVM's `-H:+RunMainInNewThread` option moves `main` off the first thread, but does not pump a run loop, so the hang remains. The feature keeps the launcher thread and pumps `CFRunLoop` on the first thread instead, in plain Java.
* Objective-C categories are dropped from static links, which shows up as an `unrecognized selector` exception when the first window opens. `libglass.a` is linked with `-force_load` to keep them.
* The application's own `Application` subclass cannot be instantiated. GraalVM's built-in JavaFX support registers `Application` subclasses for reflection, but not the no-argument constructor that the launcher actually calls, so JavaFX native images currently fail at startup with `NoSuchMethodException: MyApp.<init>()` unless the application registers itself. The feature registers the constructor of each subclass as it becomes reachable, so unused launchers in the same jar cost nothing.

As for the rendering check mentioned in the metadata section, the same binary can be pointed at the GPU pipelines (`-Dprism.order=d3d`/`es2`/`mtl`) to verify that the hardware paths render the same image as the software pipeline. The most instructive failure was a missing effect peer that no build error or exception would have caught: the first time the check drew a `DropShadow` on the software pipeline, the snapshot came back fully transparent, because the hand-written `BoxShadow` peer was not registered while its 28 generated siblings were.
