We initially used https://www.graalvm.org/native-image/[GraalVM Native Image] as a way to deploy JavaFX to mobile targets. However, after seeing significant performance benefits (GUIs mostly run in interpreted mode since users would have to click thousands of times to reach the JIT threshold), we gradually migrated all of our desktop and CLI applications over to ahead-of-time (AOT) compilation.

JavaFX actually works very well in Native Image once everything is configured, but getting a complex application running for the first time is typically not a straightforward experience. This steep initial hurdle has unfortunately earned JavaFX, and desktop Java in general, a reputation of being incompatible or working poorly with native image.

I think a big part of this stems from complex, specialized tooling that performs a lot of "magic" behind the scenes to hide the native layers. Whenever anything breaks, it produces errors that many Java developers don't know how to debug. In this post I want to demystify the internals a bit, and show how you can run the latest JavaFX 27 release with the latest Oracle GraalVM.

== Technical Background

Most native-image adopters use frameworks like https://quarkus.io/[Quarkus] or https://micronaut.io/[Micronaut] that were specifically designed for ahead-of-time compilation, and whose applications usually run on reproducible servers that the engineers control. JavaFX, on the other hand, is a rather large and highly dynamic GUI framework that predates native-image by a decade, and its applications need to run on arbitrary client machines with different operating systems.

Several layers have to work together to make this possible. In general, each solution has to solve three different problems:

1. *Reachability metadata*: Native image uses a closed-world assumption, so every resource, class, and method that gets accessed reflectively at runtime needs to be known at build time (e.g. `reachability-metadata.json`). Note that there are really two separate parts to the metadata, one part for the user's own application, and the other for the underlying JavaFX engine itself.

2. *The static binaries*: Roughly half of JavaFX is C/C++/Objective-C code (windowing, rendering, fonts, image loading, effects). A self-contained executable needs these libraries compiled as static archives, which https://github.com/openjdk/jfx[jfx] supports via `-PSTATIC_BUILD=true` but does not publish.

3. *Static integration glue*: A few things work differently under AOT and need to be bridged with glue code. For example, GraalVM's linker requires the JNI symbols of all included classes to be available at link time, even if those code paths could never actually be executed. This is an issue when, e.g., a Windows image wrongly includes a Linux font rendering class that depends on several Linux-only symbols. The resulting missing symbol errors can look cryptic to Java developers and give the impression that the binaries were not compiled correctly.

== Application Metadata

The application part of the metadata is independent of the build solutions that are the focus of this blog post, but it's by far the most common problem from a developer's perspective, so I wanted to cover it first.

On the application side, most of the reflection and resource loading comes from FXML and CSS. Desktop applications load many types of files at runtime (e.g. `.css`, `.fxml`, `.png`, `.jpg`, `.ttf`) that need to be included in the native image, and the metadata also needs to cover side-effects such as importing other resources or reflectively instantiating classes (e.g. `@import`, `-fx-skin: ${class}`, `fx:controller`).

The corresponding metadata lives in a `reachability-metadata.json` file that is hard to maintain manually and keep in sync. The typically recommended way to create the metadata is GraalVM's https://www.graalvm.org/latest/reference-manual/native-image/metadata/AutomaticMetadataCollection/[tracing agent], which attaches to a normal JVM run and traces all reflective accesses. That works reasonably well for a backend service with an automated test suite that hits every endpoint, but it is a major pain for GUI apps. Developers would have to click through every feature on every operating system, every time the app changes.

In practice, nearly every issue we encountered in production was due to agent data becoming stale. It got annoying enough that we created https://github.com/HebiRobotics/reachability-annotations[reachability-annotations], which let us define metadata via annotations that live next to the source of truth and can never go stale:

[source,java]
----
// Whenever this class is included, the resources are automatically added
@Reachable(resources = { "images/*.png" })
public class ImageLoader {}
----

We also added JavaFX-specific annotations that automatically parse `FXML/CSS` files and generate appropriate metadata for everything they reference:

[source,java]
----
@ReachableFxResources({
        "/assets/images/*.png",
        "views/**/*.fxml",
        "views/**/*.css",
})
public class MyApp extends Application {}
----

With a few annotations we can make all https://github.com/gluonhq/gluon-samples/pull/189[gluon-samples] run out of the box on all platforms without ever running an agent. By default, all entries are conditional, so unused views do not increase the image size.

Unfortunately, there are still some third-party libraries that are notoriously hard to get running, e.g., some reflection-based parsing libraries, and they may need to be replaced with something more compatible. Note that this is not specific to JavaFX, but it remains a pain point for native images in general.

== Three Approaches

So far there have been two established solutions, Gluon's Substrate and Liberica NIK. Both solve all three engine problems, but in very different ways.

=== Gluon Substrate

Gluon's Substrate is a complex toolchain that can port JavaFX to just about anything, including iOS, Android, Windows, macOS, Linux, and even small 32-bit embedded boards. It can create executables, shared and static libraries, or OS-specific bundles and installers.

Getting the whole matrix to work requires custom builds and tools for practically every layer from GraalVM to mobile wrappers and dedicated Maven and Gradle plugins. The result is quite an impressive stack, and we owe Gluon for contributing a lot of the upstream changes that let JavaFX run everywhere.

However, the number of moving targets makes for a brittle combination that can easily break at the whims of Apple or Google. According to them: "every new release of iOS, Android, the AOT compiler, the JVM components or the JDK required patches and adjustments", so they have been pivoting towards https://gluonhq.com/news/bringing-openjdk-to-mobile-a-community-effort/[OpenJDK Mobile] and a more standard open-world JDK + Leyden approach, which also makes the metadata problem disappear entirely.

That being said, the https://docs.gluonhq.com/[old tooling] still gets maintenance updates and is quite user-friendly considering the actual complexity. At the time of writing, the latest supported versions are GraalVM 23 Community Edition (CE) and JavaFX 21-ea, and I assume that we won't be able to use newer versions until the new approach becomes ready for production.

As mentioned before, we have used it for our own mobile apps, and the performance was significantly better than expected. It is still the only framework I know of that can deploy to all five targets with full 2D and 3D rendering and hot-reload of styling and layouts on several devices at once.

A common point of confusion is the licensing model. Only their https://gluonhq.com/products/gluonfx/[rich component libraries] require a license, but the build tools are free to use for all platforms.


=== BellSoft's Liberica NIK

// TODO: footnote for CE = community edition?
BellSoft took the opposite approach with https://bell-sw.com/liberica-native-image-kit/[Liberica NIK] (full) and created a dedicated GraalVM CE distribution for desktop apps. It bundles the JavaFX/Swing/AWT modules, the matching static archives, the corresponding metadata, and the glue. This way users only need to set the `GRAALVM_HOME` variable and can use it with GraalVM's stock `native-maven-plugin`.

This makes NIK by far the easiest way to get started. It is also the only route that supports AWT and Swing in native images. Swing and AWT are part of the JDK itself, so their static libraries and support code can realistically only ship inside a JDK distribution. JavaFX being decoupled from the JDK, on the other hand, is what allows anyone to provide the same integration as plain dependencies, without waiting for a vendor.

At the time of writing, they support GraalVM 25 CE with JavaFX 25 with the GPU-accelerated pipelines on the four main desktop architectures.

=== HEBI's jfx-static-feature

We have been using Liberica NIK for our desktop applications for about two years, and it has admittedly worked quite well. However, some of our applications measure https://ennerf.github.io/2016/09/20/A-Practical-Look-at-Latency-in-Robotics-The-Importance-of-Metrics-and-Operating-Systems.html[latency] at the sub-millisecond level, so even minor GC pauses in the GUI show up as incorrect measurements. A lot of code in the JDK is written assuming a powerful escape analysis (EA) that gets rid of non-escaping allocations, but the EA in the community edition (CE) that both Gluon and BellSoft build on is unfortunately quite weak. One of our worst GC causes turned out to be a simple `new double[]{a,b}` in `Math::pow`, which would never allocate on HotSpot. Since the enterprise Oracle GraalVM became free to use under the https://www.oracle.com/downloads/licenses/graal-free-license.html[GFTC] license in 2023, we wanted to move to it for the G1 GC, the better escape analysis, and other enterprise-only features like profile-guided optimization (PGO).

We also wanted to update beyond JavaFX 26+ for the new `Headless` mode, and support `linux-aarch64` and proper software-rendering fallbacks. All three were annoying issues for https://github.com/HebiRobotics/hebi-charts-examples[hebi-charts], which exposes efficient JavaFX visualizations through a native shared library to other languages via idiomatic bindings.

Neither existing approach can support the latest Oracle GraalVM with the latest JavaFX, so we had to come up with a third approach that only uses officially supported hooks into the build system. We ended up with creating two artifacts on Maven Central, `jfx-static-libs` which includes the static archives and metadata for a specific version of OpenJFX, and `jfx-static-feature` which contains the (relatively) version-agnostic glue.

GraalVM automatically picks up the included configuration files from artifacts on the classpath, so they only need to be added next to the `org.openjfx` jars as additional dependencies:

[source,xml]
----
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-feature</artifactId>
    <version>1.0</version>
</dependency>
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-libs</artifactId>
    <version>${javafx.version}</version>
    <scope>runtime</scope>
</dependency>
----

The https://github.com/ennerf/jfx-static-feature[jfx-static-feature] repository contains a complete `example-hellofx`. Once a GraalVM 25+ distribution w/ compiler toolchain is set up, you can build a self-contained executable with:

[source,shell]
----
mvn -Pnative package -pl jfx-static-examples/example-hellofx -am
----

Note that `jfx-static-libs` can also be used standalone in case you are only interested in the metadata and need it for e.g. https://medium.com/db-one/building-javafx-app-native-image-with-graalvm-new-achievement-unlocked-c5e236ecf11d[dynamic linking]. The static archives are ignored unless the matching feature is included.

=== Engine Metadata

The engine's own metadata is where the three routes differ the most. It is also the one problem the tracing agent is structurally unable to solve. Some entries depend on the operating system: the DirectWrite font backend must be registered on Windows, but must not be registered on Linux, where its reachable native methods fail the link with 65 unresolved symbols. A flat list recorded on one machine cannot express that condition. Other entries cover generated code: the shaders and effect peers are generated families of classes and resources, and the agent records only the shaders that one particular run happened to compile. The entries need to be conditional, and the agent has no way to produce conditions.

Gluon's metadata is JSON. Substrate concatenates its own bundled configs with any `META-INF/substrate/config/reflectionconfig.json` it finds in the class-path jars, and per-OS variants use separately named files, e.g., `reflectionconfig-${archOs}.json`. However, only Substrate reads these locations. The software rendering pipeline is opt-in the same way, i.e., a `usePrismSW` flag adds the `-javafxsw` config files.

NIK ships no JSON at all, which surprised me. Decompiling the `svm.jar` of NIK 25.0.3 shows a heavily extended `com.oracle.svm.hosted.javafx` package: the metadata is hand-written registration code compiled into their patched native-image, guarded by per-OS `Platform.includedIn` checks and by trigger classes like `javafx.fxml.FXMLLoader`. That is conditional metadata expressed as code. However, the knowledge is tied to the bundled JavaFX version and invisible outside NIK, and some coverage choices are baked in. For example, the registrations for the software pipeline exist in the code but are never called, so `-Dprism.order=sw` is not available on a NIK image.

The metadata that ships with `jfx-static-libs` is generated from the source instead. `@Reachable` annotations sit in the JavaFX sources next to each reflective lookup and are compiled into the jars by the regular build, so the entries are reviewable in a diff and versioned together with the code they describe. Platform-specific entries are conditioned on classes that only exist in that platform's code path, which lets a single metadata set serve all five platforms. Generated classes carry their annotations in the templates that generate them, e.g., a single annotation in the shader template covers all 212 generated shader loaders. Since the coverage describes the full engine rather than what a run happened to touch, the software pipeline works in every image. The annotation pass came to roughly 800 added lines across a bit under 200 files, which generate about 790 conditional entries and cost about 0.2% of the image size on GraalVM 25.3.

The same knowledge exists in all three routes, so the practical difference is where it lives. Metadata inside the jar moves with the JavaFX version, needs no special tooling, and works the same on any GraalVM.

Missing metadata does not fail at build time. It fails at runtime, and sometimes silently, so each release is verified by a rendering check: a headless example draws a fixed scene covering 2D, 3D, effects, dialogs, popups, and rich text, checks its own pixels, and runs on every commit on all five platforms. Beyond the synthetic scenes, the AtlantaFX sampler from the opening picture and https://www.youtube.com/watch?v=E9csKYFPwaM[Scope], our diagnostics GUI at https://hebirobotics.com/[HEBI Robotics], run as native images on real GPUs across the supported platforms. Something may still have been missed, in which case the metadata can be respun as a `${javafx.version}-1` patch release without touching the JavaFX build itself. The most instructive failure so far is described in the appendix.

There is a lot more to say about this topic, e.g., which reflective lookups native-image constant-folds on its own, and why the current metadata schema cannot express a per-OS choice. I'm planning to cover the details in a separate post.

=== The Static Libraries

The static binaries are the most mechanical problem. Upstream OpenJFX has supported static builds via `-PSTATIC_BUILD=true` for years, but has never published the resulting archives, so everyone who wanted them had to either build them or take a vendor's patched version.

The two vendors solve this in opposite ways. Substrate downloads Gluon's own static JavaFX SDK and swaps the JavaFX jars on the class path with its own before invoking native-image. That guarantees matching jars and archives, but the JavaFX that the user compiles and tests against on the JVM is not necessarily the JavaFX that ends up in the image, and the version has to be one that Gluon has published. BellSoft removes the choice entirely: NIK bundles the JavaFX modules and the matching static archives inside the JDK, so there is exactly one JavaFX in the picture.

Here, the archives come from upstream. https://github.com/ennerf/jfx[ennerf/jfx] is a fork of `openjdk/jfx` at the release tag that adds the reachability annotations and a CI workflow. There are no functional changes to the JavaFX code, i.e., the annotations only add metadata to the jars, and the fork is two commits per release. For each release, CI builds the static SDK for `windows-x86_64`, `linux-x86_64`, `linux-aarch64`, `darwin-x86_64`, and `darwin-aarch64`. Note that the Linux builds run on the oldest supported Ubuntu LTS, because the build host's headers determine the oldest glibc the archives can link against.

`jfx-static-libs` packages every platform's archives together with the metadata into a single jar of roughly 10 MB, without any classifier. Packaging all platforms into one artifact removes the need for OS detection, Maven profiles, and per-platform classifiers, and Maven and Gradle resolve it identically. The archives of the other platforms only cost a one-time download, since no resource configuration references them and they never enter an image.

One constraint that dynamic linking hides is that the Java classes and the native archives have to come from the same JavaFX build. The JNI side of JavaFX is not a stable interface, and a mismatch shows up as an undefined symbol at link time. `jfx-static-libs` is therefore versioned by the JavaFX release it was built from and declared with the same `${javafx.version}` property as the `org.openjfx` jars. If the versions still disagree, e.g., due to a stale pin in a parent pom, the feature aborts the build with a message that names both rather than failing with a linker error. The feature itself has its own version line, since the substitutions have not had to follow a JavaFX change in years.

=== Integration Glue

Linking the archives into an image is the last problem: something has to tell native-image that the JavaFX native code is compiled into the image rather than loaded from shared libraries, and work around the places where GraalVM and a statically linked JavaFX do not fit together yet.

This is handled by `jfx-static-feature`, a GraalVM https://www.graalvm.org/sdk/javadoc/org/graalvm/nativeimage/hosted/Feature.html[Feature] that is picked up from the class path by any stock native-image. It registers the JNI package prefixes as builtin, adds the platform's archives as static JNI libraries, and names the system libraries they reference, i.e., GTK on Linux and the Cocoa frameworks on macOS, which stay dynamic (see Trade-offs). Doing this in a feature keeps the list out of every consumer's build without patching anything.

==== Removing the Need for C Stubs

GraalVM's analysis keeps the font and image backends of the other platforms reachable. For example, when building on Windows, the Linux freetype code and the macOS CoreText code are still on the class path and still reachable, but the Windows archives contain none of their native methods, and every unresolved native method in a static JNI library is a link error. Even perfectly conditional metadata does not help here, because the analysis reaches these classes on its own. The obvious fix is a small C stub for each missing function, which in this case would have been around 45 stubs per platform.

I wanted to avoid this: custom C stubs would need a matching toolchain on every platform and would have to match the JavaFX version exactly, so they would only really be safe if they were generated inside the JavaFX build itself.

Instead, the feature uses GraalVM's `@Delete` substitution to remove those classes from the analysis entirely, so their native methods are never reachable and never need to resolve. This is plain Java, independent of the JavaFX version, and requires no toolchain beyond what native-image already needs. The conditions are negations (`NotLinux`, `NotMacOS`) rather than inclusion lists, so a future iOS or Android port would fail visibly instead of silently keeping a stubbed-out backend.

Beyond the deletions, the feature contains a small number of substitutions that work around remaining gaps between GraalVM and a statically linked JavaFX, e.g., calling the `JNI_OnLoad` initializers directly and pumping a Cocoa run loop on the first thread on macOS. The appendix lists them individually.

== Trade-offs

There are a few limitations that are worth being clear about:

* *System libraries.* The image contains all of the JavaFX native code, but GTK on Linux and the Cocoa frameworks on macOS are dynamic dependencies, the same as for any native application. Any machine that can run GTK applications has everything the image needs.
* *Raspberry Pi.* JavaFX qualifies GPUs using a vendor allowlist that predates the Pi's Mesa V3D driver, so the es2 pipeline requires `-Dprism.forceGPU=true` and otherwise falls back to software rendering. The upstream fix is a one-line addition to the allowlist.


== Appendix: The Remaining Glue

This section collects the individual workarounds inside `jfx-static-feature` for readers who run into the corresponding errors, or who want to fix the underlying issues. None of them are application specific, and most of them belong upstream, either in GraalVM or in OpenJFX:

* `System.loadLibrary` cannot load any of the static JavaFX libraries. On Windows, glass reports JNI version 1.2 from its `JNI_OnLoad`, while the spec requires 1.8 or later for statically linked libraries (an upstream bug with a one-line fix). On Linux and macOS, the `JNI_OnLoad_<lib>` symbols are hidden by the image's linker version script. The feature calls the initializers directly.
* Overloaded native methods never link, because Substrate resolves builtin JNI methods by their short name, and an overloaded native only exists under its signature-mangled name on the C side. The four `directwrite.OS` overloads on Windows, and `MacTimer._start` and `coretext.OS.CFStringCreateWithCharacters` on macOS, are routed to the mangled symbols via `@CFunction` substitutions.
* On macOS, the process hangs before the first window appears. Cocoa requires the first thread of the process to be pumping a run loop while glass starts up. The `java` launcher arranges this, but a native image runs `main` on the first thread. This has been known since https://github.com/oracle/graal/issues/994[2019], and the common answer has been an external Objective-C launcher. GraalVM's `-H:+RunMainInNewThread` option moves `main` off the first thread, but does not pump a run loop, so the hang remains. The feature keeps the launcher thread and pumps `CFRunLoop` on the first thread instead, in plain Java.
* Objective-C categories are dropped from static links, which shows up as an `unrecognized selector` exception when the first window opens. `libglass.a` is linked with `-force_load` to keep them.
* The application's own `Application` subclass cannot be instantiated. GraalVM's built-in JavaFX support registers `Application` subclasses for reflection, but not the no-argument constructor that the launcher actually calls, so JavaFX native images currently fail at startup with `NoSuchMethodException: MyApp.<init>()` unless the application registers itself. The feature registers the constructor of each subclass as it becomes reachable, so unused launchers in the same jar cost nothing.

As for the rendering check mentioned in the metadata section, the same binary can be pointed at the GPU pipelines (`-Dprism.order=d3d`/`es2`/`mtl`) to verify that the hardware paths render the same image as the software pipeline. The most instructive failure was a missing effect peer that no build error or exception would have caught: the first time the check drew a `DropShadow` on the software pipeline, the snapshot came back fully transparent, because the hand-written `BoxShadow` peer was not registered while its 28 generated siblings were.
