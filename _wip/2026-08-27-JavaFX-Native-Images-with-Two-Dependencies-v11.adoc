We initially used https://www.graalvm.org/native-image/[GraalVM Native Image] as a way to deploy JavaFX to mobile targets. However, after seeing significant performance benefits (GUIs mostly run in interpreted mode since users would have to click thousands of times to reach the JIT threshold), we gradually migrated all of our desktop and CLI applications over to ahead-of-time (AOT) compilation.

JavaFX actually works very well in Native Image once everything is configured, but getting a complex application running for the first time is typically not a straightforward experience. This steep initial hurdle has unfortunately earned JavaFX, and desktop Java in general, a reputation of being incompatible or working poorly with native image.

I think a big part of this stems from complex, specialized tooling that performs a lot of "magic" behind the scenes to hide the native layers. Whenever anything breaks, it produces errors that many Java developers don't know how to debug. In this post I want to demystify the internals a bit, and show how you can run the latest JavaFX 27 release with the latest Oracle GraalVM.

== Three Approaches

Most native-image adopters use frameworks like https://quarkus.io/[Quarkus] or https://micronaut.io/[Micronaut] that were specifically designed for ahead-of-time compilation, and whose applications usually run on reproducible servers that the engineers control. JavaFX, on the other hand, is a rather large and highly dynamic GUI framework that predates native-image by a decade, and its applications need to run on arbitrary client machines with different operating systems.

Making that whole stack work requires dedicated solutions. There are two established ones, Gluon's Substrate and BellSoft's Liberica NIK, and we just released our `jfx-static-feature` accompanying this blog post.


=== Gluon Substrate

Gluon's Substrate is a complex toolchain that can port JavaFX to just about anything, including iOS, Android, Windows, macOS, Linux, and even small 32-bit embedded boards. It can create executables with and without JavaFX, shared and static libraries, deal with resources, add custom C extensions, build OS-specific bundles and installers, and even do remote deployments to small targets via ssh.

Getting all of that to work requires modified builds and custom tools for practically every layer starting at the GraalVM distribution to mobile tooling and dedicated Maven and Gradle plugins. The result is quite an impressive stack, and Gluon deserves credit for contributing a lot of the upstream changes that let JavaFX run everywhere.

However, the number of moving targets makes for a brittle combination that can easily break. According to Gluon: "every new release of iOS, Android, the AOT compiler, the JVM components or the JDK required patches and adjustments", so they have been pivoting towards https://gluonhq.com/news/bringing-openjdk-to-mobile-a-community-effort/[OpenJDK Mobile], which is a more standard JDK + Leyden approach. Moving to an open-world model will also make it easier for users as it removes the metadata problem.

That being said, the existing tooling still gets maintenance updates (link:https://docs.gluonhq.com/[see docs]) and is comparably user-friendly considering the enormous underlying complexity. At the time of writing, the latest versions supported by Gluon are GraalVM 23 Community Edition (CE) and JavaFX 21-ea. On desktop, there is also unofficial support for building with other GraalVM distributions, but there is currently no way to use a newer JavaFX release.

We've used Gluon's tools internally for 1-2 years and are still using it for mobile targets. JavaFX on mobile actually works far better than we originally expected, and it's really nice to be able to deploy to all five targets with full 2D and 3D rendering as well as hot-reload of styling and layouts.

A common point of confusion is the licensing model. Only their https://gluonhq.com/products/gluonfx/[rich component libraries] require a license, but the build tools are free to use for all platforms.


=== BellSoft's Liberica NIK

BellSoft took a much more focused approach and created a GraalVM CE distribution dedicated to desktop apps: https://bell-sw.com/liberica-native-image-kit/[Liberica NIK (full)].

Their distribution bundles both JavaFX and Swing/AWT modules, as well as corresponding metadata. Users only need to set `GRAALVM_HOME` and can use it with GraalVM's stock `native-maven-plugin`. If you need to get something running quickly, NIK is the easiest way to get started on desktop apps.

Liberica NIK is currently also the only supported way to run AWT and Swing in native images. Note that even a stock Oracle GraalVM ships the static AWT archives, but they are useless without the matching metadata and integration code that NIK provides. In a way, the decoupling of JavaFX from the JDK turned out to be a blessing in disguise because it can be treated like a normal library that we can update at will without needing vendor support.

At the time of writing, NIK (full) supports the LTS versions GraalVM 25 CE with JavaFX 25 and the GPU-accelerated pipelines on the four main desktop architectures. They currently do not support the software pipeline or `linux-aarch64` targets.

=== HEBI's jfx-static-feature

We have been using Liberica NIK for our desktop applications for about two years, and it has admittedly worked quite well.

However, some of our applications measure https://ennerf.github.io/2016/09/20/A-Practical-Look-at-Latency-in-Robotics-The-Importance-of-Metrics-and-Operating-Systems.html[latency] at the sub-millisecond level, and we ran into issues with incorrect measurements due to poor escape analysis and GC behavior in the community edition. Our worst allocation source turned out to be a simple `new double[]{a,b}` in `Math::pow`, which would never allocate on HotSpot. Since the enterprise Oracle GraalVM became free to use under the https://www.oracle.com/downloads/licenses/graal-free-license.html[GFTC] license in 2023, we wanted to switch to get the G1 GC, the better escape analysis, and other enterprise-only features like profile-guided optimization (PGO).

We also needed to upgrade to a newer JavaFX version for https://github.com/HebiRobotics/hebi-charts-examples[hebi-charts], which exposes high-performance JavaFX visualizations through a native shared library to other languages like Python and C++. Our goal was to be able to generate graphics/images through SSH on a linux-aarch64 device using the `Headless` mode introduced in JavaFX 26 with the software pipeline.

Neither Substrate nor Liberica NIK supports that specific combination, so we ended up creating https://github.com/ennerf/jfx-static-feature[jfx-static-feature]. Rather than taking over the build system, it only uses officially supported GraalVM hooks.

It consists of two artifacts: `jfx-static-libs` for version-specific static archives and metadata, and `jfx-static-feature` for some (relatively) version-agnostic glue. GraalVM automatically picks up configuration files from artifacts on the classpath, so users only need to add two dependencies next to the `org.openjfx` jars:

[source,xml]
----
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-feature</artifactId>
    <version>1.0</version>
</dependency>
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-libs</artifactId>
    <version>${javafx.version}</version>
    <scope>runtime</scope>
</dependency>
----

All of the required jvm flags, linker options, JSON configuration files, and OS-specific profiles are provided internally. The https://github.com/ennerf/jfx-static-feature[jfx-static-feature] repository contains a complete `example-hellofx`. Once a GraalVM 25+ distribution and a matching C toolchain are set up, you can build a self-contained executable with:

[source,shell]
----
mvn -Pnative package -pl jfx-static-examples/example-hellofx -am
----

Note that `jfx-static-libs` can also be used standalone in case you are only interested in the metadata and need it for https://medium.com/db-one/building-javafx-app-native-image-with-graalvm-new-achievement-unlocked-c5e236ecf11d[dynamic linking]. The static archives are ignored unless the matching feature is included.


== Three Problems

Several layers have to work together to make JavaFX run as a native image. In general, there are three problems that need to be addressed:

1. *Reachability metadata*: Native image uses a closed-world assumption, so every resource, class, and method that gets accessed reflectively at runtime needs to be known at build time (e.g. `reachability-metadata.json`). The metadata consists of two separate parts: the metadata specific to the user's application, and the generic metadata for the underlying engine. The engine metadata is tied to the JavaFX version and operating system.

2. *The static binaries*: Roughly half of JavaFX is C/C++/Objective-C code (windowing, rendering, fonts, image loading, effects). A self-contained executable needs these libraries compiled and linked in as static archives. https://github.com/openjdk/jfx[jfx] already supports building the archives via `-PSTATIC_BUILD=true`, but they currently don't get published.

3. *Static integration glue*: A few things work differently under AOT and need to be bridged with glue code. For example, GraalVM's linking step requires the native symbols of all included classes to be available at link time, even if some code paths could never be reached. This is an issue when, e.g., a Windows image wrongly includes a Linux font rendering class that uses JNI and depends on several Linux-only symbols. The resulting missing symbol errors can look cryptic to Java developers and give the impression that the binaries were not compiled correctly.

=== Application Metadata

The application part of the metadata is independent of the build solutions that are the focus of this blog post, but it's by far the most common problem from a developer's perspective, so I want to cover it before the engine parts.

On the application side, most of the reflection and resource loading comes from FXML and CSS. Desktop applications load many types of files at runtime (e.g. `.css`, `.fxml`, `.png`, `.jpg`, `.ttf`) that need to be included in the native image, and the metadata also needs to cover side-effects such as importing other resources or reflectively instantiating classes (e.g. `@import`, `-fx-skin`, `fx:controller`).

The corresponding metadata lives in a `reachability-metadata.json` file that is hard to maintain manually and keep in sync. The typically recommended way to create the metadata is GraalVM's https://www.graalvm.org/latest/reference-manual/native-image/metadata/AutomaticMetadataCollection/[tracing agent], which attaches to a normal JVM run and traces all reflective accesses. That works reasonably well for a backend service with an automated test suite that hits every endpoint, but it is a major pain for GUI apps. Developers would have to click through every feature on every operating system, and redo it every time the app changes.

In practice, nearly every issue we encountered in production was due to agent data becoming stale. It got annoying enough that we created https://github.com/HebiRobotics/reachability-annotations[reachability-annotations], which let us define metadata via annotations that live next to the source of truth and can never go out of sync:

[source,java]
----
// Whenever this class is included, the resources are automatically added
@Reachable(resources = { "images/*.png" })
public class ImageLoader {}
----

We also added some JavaFX-specific annotations that automatically parse `FXML/CSS` files and generate appropriate metadata for everything they reference:

[source,java]
----
@ReachableFxResources({
        "/assets/images/*.png",
        "views/**/*.fxml",
        "views/**/*.css",
})
public class MyApp extends Application {}
----

With a few annotations we can make all https://github.com/gluonhq/gluon-samples/pull/189[gluon-samples] run out of the box on all platforms without ever running an agent. Even our most complex apps do not use the agent anymore outside of explorative runs. By default, all entries are conditional, so unused views do not increase the image size.

Unfortunately, there are still some third-party libraries that are notoriously hard to get running, e.g., some reflection-based parsing libraries, and they may need to be replaced with something more compatible. Note that this is not specific to JavaFX, but it remains a pain point for native images in general.

=== Engine Metadata

Unlike the application metadata, the engine metadata is constant for a specific version and operating system. Users only see a pure Java API, but internally there is a lot of native code for dealing with OS behavior and rendering pipelines, and a lot of reflection to pick appropriate implementations at runtime. Between the reflection, JNI, and resources (shaders, css files, fonts, etc.), it currently takes close to 800 metadata entries to cover the whole framework.

Additionally, a lot of the metadata only applies to specific operating systems. Many of the platform-specific classes (e.g. `WinApplication.class`) get filtered out of the platform jars, but a few classes (e.g. platform fonts) are always available. Adding those unnecessarily bloats the native-image, and can even break the build. For example, accidentally adding the Windows DirectWrite font backend on Linux results in 65 unresolved symbols at link time even though none of those symbols are needed.

The metadata cannot be generated with an agent as it is impossible to cover all possible paths in a single application. The shaders and effects alone form a large family of generated classes, each run is limited to a single pipeline, and some accesses even depend on the class loading order. Therefore, this metadata needs to be curated in some way, and ideally use wildcards to cover all shaders at once.

**Substrate** bundles JSON metadata with their downloaded fx jars (`META-INF/substrate/config/reflectionconfig.json`), and adds a custom mechanism that conditionally appends target-specific metadata (e.g. `reflectionconfig-x86_64-linux.json`) and optional metadata (e.g. `-javafxsw` with `-DusePrismSW` for the software pipeline) before handing it to native-image. Only Substrate knows about these suffixes, so the metadata does not work when using the stock `native-maven-plugin`.

**Liberica NIK** ships no JSON files at all. Instead, they heavily extended the https://github.com/oracle/graal/blob/6d71c876640c9ae7b3c131ebecc8d1834ac813c7/substratevm/src/com.oracle.svm.hosted/src/com/oracle/svm/hosted/javafx/JavaFXFeature.java[com.oracle.svm.hosted.javafx.JavaFXFeature] in the `svm.jar` and register rules directly from code. The metadata is tied to the bundled jfx version, and the conditions are generated using `Platform.includedIn` checks and triggers on specific classes.

**jfx-static-libs** ships conventional JSON files with conditions that approximate OS filtering, e.g., `isReachable(${OS}Application.class)`. This is compatible with the stock tooling, so it works out of the box with any GraalVM version. The metadata itself is currently generated using `@Reachable` annotations in my https://github.com/ennerf/jfx/tree/jfx26u-metadata[ennerf/jfx] fork and updated once per release.

=== The Static Libraries

The static binaries are primarily a distribution problem. Upstream OpenJFX has supported static builds via `-PSTATIC_BUILD=true` for years, but has never published the resulting archives. Everyone who needs them has to rely on 3rd party vendors or build the archives themselves. One issue with that is that the versions have to be an exact match, i.e., they should be built from the same commit as the runtime jars.

// ANSWER (2026-09-11, substrate source): version via javafxStaticSdkVersion property

**Substrate** downloads Gluon's own static JavaFX SDK and silently replaces the user-specified JavaFX jars before invoking native-image. This ensures matching jars and archives, but it's impossible to use a newer version. If you currently specify jfx version 27, it gets switched to the latest Gluon build and reported as `21-internal+11.2`. Substrate offers a hook to downgrade to older versions, but at the moment there is no way to set a custom url to use a newer non-Gluon build. By default Substrate only adds the hardware pipelines. The software fallback is opt-in via the plugin's `enableSWRendering` flag. Note that our first test spelled it `enableSwRendering`, which Maven silently ignores, so the fallback looked broken even though it works fine once enabled.

The builds currently live in my openjfx fork at https://github.com/ennerf/jfx[ennerf/jfx]. We do not modify any JFX code or behavior, so the behavior is identical with running on Hotspot. However, each release adds two commits for setting up the annotation processor and annotations for generating the metadata. We decided to match Substrate's format for the produced artifacts in case Substrate ever accepts custom download urls.

=== Integration Glue

Lastly, we need the glue required for adding the actual linking arguments and fixing some pitfalls that show up during static linking.

**Substrate** owns the entire build chain, so all linker arguments live inside their build tool. Note that on Linux they additionally enable an internal `GluonFeature` that registers the JavaFX libraries as built-in JNI libraries, similar to what our feature does on all platforms.
// NOTE (verified 2026-09-11 in substrate source): GluonFeature is Linux-only
//  (LinuxTargetConfiguration.getEnabledFeatures; source comment: "for now, it is
//  linux-supported only"). It preregisters prism_sw, prism_es2, glass, glass_monocle,
//  glassgtk3 and adds prefixes com_sun_glass, com_sun_prism, com_sun_pisces,
//  com_sun_javafx_font_freetype, com_sun_javafx_font_FontConfigManager,
//  com_sun_javafx_iio_jpeg. Needs --add-exports for SVM internals.

**Liberica NIK** leaves the build tools alone. Users run the stock `native-maven-plugin`, and all changes live in the patched `native-image` builder itself, i.e., a `JavaFXFeature` compiled into their `svm.jar` that registers the libraries and metadata for the bundled JavaFX version.
// NOTE (verified 2026-09-11): svm.jar contains com.oracle.svm.hosted.javafx
//  JavaFXFeature/JavaFXJNI/JavaFXReflection + JavaFXPresent; same builtin registration
//  mechanism as ours, per-OS curated.

**jfx-static-feature** was designed to work with the stock build tool, so it is implemented as a GraalVM https://www.graalvm.org/sdk/javadoc/org/graalvm/nativeimage/hosted/Feature.html[Feature] that gets picked up from the classpath automatically. It extracts the platform-specific archives, checks that they match the runtime version, and adds the necessary linker commands for the static libraries and their system dependencies, e.g., Cocoa on macOS or GTK on Linux (those stay dynamic).


==== Linking Missing Symbols

As mentioned in the metadata section, a few platform-specific classes are present in every platform's jar even though their native code is not. Out of the 95 graphics classes that declare native methods, this only applies to six classes related to font rendering, as well as the iOS image loader.

Unfortunately, even with perfectly provided metadata, users can easily cause issues by e.g. committing agent-generated files and building on another platform. Until those classes are filtered upstream (TODO: link to filter), making e.g. the Windows DirectWrite font backend reachable on Linux breaks the build with 65 unresolved symbols even though none of them are needed. The missing symbol errors look more like a broken toolchain rather than metadata issue, and give the impression that the binaries were not compiled correctly.

[source]
----
helloworld-graal.obj : error LNK2001: unresolved external symbol
                       Java_com_sun_javafx_font_coretext_OS_CFArrayGetCount
[... 54 more unresolved CoreText symbols ...]
helloworld-graal.exe : fatal error LNK1120: 55 unresolved externals
----

The obvious fix would be providing small C stubs that cover missing dummy symbols, but that would come out to dozens of stubs per platform that would need to be bundled with the archives and would represent yet another thing to maintain.

Note that all three approaches build on the same underlying mechanism: native-image only creates link-time references for native methods that belong to a registered built-in library, and treats everything else as regular JNI that resolves at runtime. Registering a library as built-in therefore turns every reachable native method into a symbol that the linker has to find, and a missing implementation into a build error. The difference is how much gets registered.

// NOTE (verified 2026-09-11): Windows passes each fx lib BOTH as normal input and as
//  /WHOLEARCHIVE:<lib> (plain inputs redundant; symbol-level dead stripping never happens
//  there). Linux: plain -l flags, LinuxLinkerFlags hardwires -Wl,--no-whole-archive;
//  -rdynamic is always set, independent of JavaFX.
// NOTE other GraalVMs (pending build test): vendor check only LOGS a warning without
//  VENDOR=Gluon; version floor check is a no-op for JDK>=20. GluonFeature's internal API
//  still exists in 25.x, so "newer ones will fail" is NOT confirmed.
**Substrate** gets around this by forcing the whole archives into the image and resolving symbols lazily at runtime (`/WHOLEARCHIVE` on Windows and `-force_load` on macOS), which is similar to the JVM. On the other hand, this disables build time verification and pushes actual errors to runtime. A missing implementation shows up at the first call as an `UnsatisfiedLinkError` pointing at the `java.library.path`, which sends developers looking for a shared library that was never supposed to exist. The Linux builds are the exception: there the archives get linked normally, and the `GluonFeature` registers a curated prefix list that leaves out the wrong-OS font backends, so their symbols are never referenced.

**Liberica NIK** also binds the native methods at link time, but their `JavaFXFeature` only registers the font classes that belong to the current platform. The wrong-OS classes can still enter the image through bad metadata, but their natives get treated as regular JNI and fail at the first call instead of the build.
// NOTE (verified 2026-09-11, svm.jar disassembly): purely omission via a per-OS allow-list
//  (Platform.includedIn chain: WINDOWS -> PrismFontFactory+directwrite; LINUX ->
//  FontConfigManager+freetype; DARWIN -> DFontDecoder+MacFontFinder+coretext). No jar
//  patching, no @Delete/@Substitute on platform classes (byte-level grep found none).

**jfx-static-feature** makes use of GraalVM's `@Delete` substitution to delete unwanted classes and solve the problem at the root. Classes that are not part of the analysis are never deemed reachable and never need to resolve. The static archives are linked normally, so actually missing symbols will fail eagerly at link time.

// Code verbatim from jfx-static-feature stubs/DeleteLinuxNatives.java + ClassPresent.java
// (2026-09-11). Also in the stubs but not shown: a method-level @Delete for the dead
// upstream declaration OSFreetype.FT_Get_Char_Index (implemented in no archive on any OS).
[source,java]
----
@Delete
@TargetClass(className = "com.sun.javafx.font.freetype.FTFactory",
        onlyWith = {NotLinux.class, ClassPresent.class})
static final class Target_FTFactory {
}

static final class NotLinux implements BooleanSupplier {
    public boolean getAsBoolean() {
        return !Platform.includedIn(Platform.LINUX.class);
    }
}

// SVM evaluates Predicate<String> conditions on the class NAME before
// resolving the target, so a removed upstream class skips the stub
final class ClassPresent implements Predicate<String> {
    @Override
    public boolean test(String className) {
        try {
            Class.forName(className, false, ClassPresent.class.getClassLoader());
            return true;
        } catch (ClassNotFoundException e) {
            return false;
        }
    }
}
----

The conditions are negations (`NotLinux`, `NotMacOS`) rather than inclusion lists, so a future iOS or Android port would fail visibly instead of silently keeping a stubbed-out backend. Each deletion is also guarded by a check that the target class actually exists, so a future upstream cleanup removes the stub instead of breaking the build. The triple negation is a bit hard to read, but it keeps the classes out of any target that they were not meant for.

Note that `PrismFontFactory` cannot be deleted as a whole because its Windows-only natives sit on the shared base class. Those six methods get substituted individually with stubs that throw an exception.

We tested the individual mechanisms by adding a bad metadata file that makes all JNI classes fully reachable and tried building all three versions. Substrate built without issue on Windows and macOS. The default Linux build failed with twenty missing symbols from the software pipeline, i.e., an archive that only gets linked when the sw flag is enabled. With the flag, the only remaining failure was the dead `FT_Get_Char_Index` declaration that no platform ever implemented. For NIK we encountered one unresolved symbol in `com.sun.glass.ui.Application` due to a method that was added in JavaFX 24 and lives in `prism_common`. Note that none of these issues were related to the wrong-OS classes.

==== Remaining Glue

Beyond the deletions, `jfx-static-feature` also contains a small number of substitutions that work around remaining gaps between GraalVM and a statically linked JavaFX. Several of them are latent issues that wouldn't show up on a JVM, but should be fixed upstream. I didn't check how Gluon/NIK handles each of them:

// TODO: reword below to sound less like AI?

**GraalVM**

* Overloaded native methods never link. Native-image resolves builtin JNI methods by their short name, and an overloaded native only exists under its signature-mangled name on the C side (hits `directwrite.OS`, `MacTimer._start`, and `coretext.OS.CFStringCreateWithCharacters`). We added `@CFunction` substitutions to manually route them to the mangled symbols.

* GraalVM's built-in JavaFX support registers `Application` subclasses for reflection, but not the no-argument constructor that the launcher actually calls. JavaFX native images currently fail at startup with `NoSuchMethodException: MyApp.<init>()` unless the application registers itself. Our feature registers the constructor of each reachable subclass to provide a better out of the box experience.

**OpenJFX**

* `System.loadLibrary` cannot load any of the static JavaFX libraries. On Windows, glass reports JNI version 1.2 from its `JNI_OnLoad`, while the spec requires 1.8 or later for statically linked libraries (one-line fix). On Linux and macOS, the `JNI_OnLoad_<lib>` symbols are hidden by the image's linker version script, so the feature calls the initializers directly.
// NOTE (2026-09-11): GraalVM 25 now enforces the >=1.8 rule at runtime for builtin
//  libraries (JNIVersion.isSupported). Observed in practice: the Gluon-on-Oracle-25 test
//  died with "UnsatisfiedLinkError: Unsupported JNI version 0x10006, required by glass"
//  (Linux glass returns 1.6). Same upstream bug family as the Windows 1.2 case.

* Objective-C categories are dropped from static links, which shows up as an `unrecognized selector` exception when the first window opens. `libglass.a` is linked with `-force_load` to keep them.

// TODO: is this a JFX or GraalVM issue? Gluon has an AppDelegate.m file. What about Liberica NIK? Would those work in shared libs - I assume not?
// ANSWER Gluon (2026-09-11, substrate native/macosx): AppDelegate.m keeps thread 1 inside
//  [NSApp run] and starts the Java main on a BACKGROUND thread from
//  applicationDidFinishLaunching (performSelectorInBackground -> run_main). launcher.c
//  just calls into it; excluded for shared-library builds, so shared libs indeed get no
//  run loop from Gluon. NIK on macOS: could not verify from a Windows install (no macOS
//  artifacts present) -- needs a macOS NIK distribution or their docs.
* On macOS, the process hangs before the first window appears. Cocoa requires the first thread of the process to be pumping a run loop while glass starts up. The `java` launcher arranges this, but a native image runs `main` on the first thread. This has been known since https://github.com/oracle/graal/issues/994[2019], and the common answer has been an external Objective-C launcher. GraalVM's `-H:+RunMainInNewThread` option moves `main` off the first thread, but does not pump a run loop, so the hang remains. The feature keeps the launcher thread and pumps `CFRunLoop` on the first thread instead, in plain Java.

* JavaFX qualifies GPUs using a vendor allowlist that predates the Raspberry Pi's Mesa V3D driver, so the es2 pipeline requires `-Dprism.forceGPU=true` to avoid falling back to software rendering. The GPU would have to be added to the allowlist or needs to be worked around at the application level.

== Trade-offs

There are a few limitations that are worth being clear about:

* *System libraries.* The image contains all of the JavaFX native code, but GTK on Linux and the Cocoa frameworks on macOS are dynamic dependencies, the same as for any native application. Any machine that can run GTK applications has everything the image needs.

* *Image size.* A minimal application comes out at roughly 46 MB on Windows and 52 MB on Linux, i.e., in the same range as Liberica NIK and noticeably smaller than Gluon Substrate. Note that each stack links a different JavaFX version even when the poms declare the same one, so the numbers are only rough guidance:
