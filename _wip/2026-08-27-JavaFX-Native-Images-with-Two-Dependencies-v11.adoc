We initially used https://www.graalvm.org/native-image/[GraalVM Native Image] as a way to deploy JavaFX to mobile targets. However, after seeing significant performance benefits (GUIs mostly run in interpreted mode since users would have to click thousands of times to reach the JIT threshold), we gradually migrated all of our desktop and CLI applications over to ahead-of-time (AOT) compilation.

JavaFX actually works very well in Native Image once everything is configured, but getting a complex application running for the first time is typically not a straightforward experience. This steep initial hurdle has unfortunately earned JavaFX, and desktop Java in general, a reputation of being incompatible or working poorly with native image.

I think a big part of this stems from complex, specialized tooling that performs a lot of "magic" behind the scenes to hide the native layers. Whenever anything breaks, it produces errors that many Java developers don't know how to debug. In this post I want to demystify the internals a bit, and show how you can run the latest JavaFX 27 release with the latest Oracle GraalVM.

== Three Approaches

Most native-image adopters use frameworks like https://quarkus.io/[Quarkus] or https://micronaut.io/[Micronaut] that were specifically designed for ahead-of-time compilation, and whose applications usually run on reproducible servers that the engineers control. JavaFX, on the other hand, is a rather large and highly dynamic GUI framework that predates native-image by a decade, and its applications need to run on arbitrary client machines with different operating systems.

Making that whole stack work requires dedicated solutions. There are two established ones, Gluon's Substrate and BellSoft's Liberica NIK, and we just released another one accompanying this blog post.


=== Gluon Substrate

Gluon's Substrate is a complex toolchain that can port JavaFX to just about anything, including iOS, Android, Windows, macOS, Linux, and even small 32-bit embedded boards. It can create executables, shared and static libraries, or OS-specific bundles and installers.

Getting the whole matrix to work requires custom builds and tools for practically every layer from GraalVM to mobile wrappers and dedicated Maven and Gradle plugins. The result is quite an impressive stack, and Gluon deserves credit for contributing a lot of the upstream changes that let JavaFX run everywhere.

However, the number of moving targets makes for a brittle combination that can easily break at the whims of Apple or Google. According to Gluon: "every new release of iOS, Android, the AOT compiler, the JVM components or the JDK required patches and adjustments", so they have been pivoting towards https://gluonhq.com/news/bringing-openjdk-to-mobile-a-community-effort/[OpenJDK Mobile], i.e., a more standard JDK + Leyden approach. Moving to an open-world model will also make it easier for users as it removes the metadata problem.

That being said, the https://docs.gluonhq.com/[old tooling] still gets maintenance updates and is quite user-friendly considering the actual complexity. At the time of writing, the latest supported versions are GraalVM 23 Community Edition (CE) and JavaFX 21-ea. On desktop, there is also unofficial support for using other GraalVM versions, but I assume that we won't see any newer JavaFX versions until the new approach becomes ready for production.

Internally, we've used Gluon's tools for 1-2 years and are still using it for mobile targets. JavaFX on mobile actually works far better than we originally expected, and it's really nice to be able to deploy to all five targets with full 2D and 3D rendering as well as hot-reload of styling and layouts.

A common point of confusion is the licensing model. Only their https://gluonhq.com/products/gluonfx/[rich component libraries] require a license, but the build tools are free to use for all platforms.


=== BellSoft's Liberica NIK

BellSoft took a much more focused approach and created a GraalVM CE distribution dedicated to desktop apps: https://bell-sw.com/liberica-native-image-kit/[Liberica NIK] (full).

Besides JavaFX, it also bundles Swing/AWT modules and corresponding metadata. Users only need to set `GRAALVM_HOME` and can use it with GraalVM's stock `native-maven-plugin`. If you need to get something running quickly, NIK is the easiest way to get started on desktop apps.

Liberica NIK is currently also the only supported way to run AWT and Swing in native images. Note that even a stock GraalVM ships the static AWT archives, but they are useless without the matching metadata and integration code, which NIK compiles into their patched native-image. In a way, the decoupling of JavaFX from the JDK turned out to be a blessing in disguise because it can be treated like a normal library that we can update at will without needing vendor support.

At the time of writing, NIK (full) supports GraalVM 25 CE with JavaFX 25 and the GPU-accelerated pipelines on the four main desktop architectures (i.e. no software fallbacks and no `linux-aarch64` targets).


=== HEBI's jfx-static-feature

We have been using Liberica NIK for our desktop applications for about two years, and it has admittedly worked quite well.

However, some of our applications measure https://ennerf.github.io/2016/09/20/A-Practical-Look-at-Latency-in-Robotics-The-Importance-of-Metrics-and-Operating-Systems.html[latency] at the sub-millisecond level, and we ran into issues with incorrect measurements due to poor escape analysis and GC behavior in the community edition. Our worst allocation source turned out to be a simple `new double[]{a,b}` in `Math::pow`, which would never allocate on HotSpot. Since the enterprise Oracle GraalVM became free to use under the https://www.oracle.com/downloads/licenses/graal-free-license.html[GFTC] license in 2023, we wanted to switch to get the G1 GC, the better escape analysis, and other enterprise-only features like profile-guided optimization (PGO).

We also wanted to update to at least JavaFX 26 for the new `Headless` mode, and support `linux-aarch64` and proper software-rendering fallbacks. All three were annoying issues for https://github.com/HebiRobotics/hebi-charts-examples[hebi-charts], which exposes efficient JavaFX visualizations through a native shared library to other languages via idiomatic bindings.

Neither Substrate nor NIK supports the latest Oracle GraalVM with the latest JavaFX, so we created https://github.com/ennerf/jfx-static-feature[jfx-static-feature], which only uses officially supported hooks into the build system. It consists of two artifacts: `jfx-static-libs` for version-specific static archives and metadata, and `jfx-static-feature` for some (relatively) version-agnostic glue. GraalVM automatically picks up configuration files from artifacts on the classpath, so users only need to add two dependencies next to the `org.openjfx` jars:

[source,xml]
----
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-feature</artifactId>
    <version>1.0</version>
</dependency>
<dependency>
    <groupId>us.hebi.graalvm</groupId>
    <artifactId>jfx-static-libs</artifactId>
    <version>${javafx.version}</version>
    <scope>runtime</scope>
</dependency>
----

All of the required jvm flags, linker options, JSON configuration files, and OS-specific profiles are provided internally. The https://github.com/ennerf/jfx-static-feature[jfx-static-feature] repository contains a complete `example-hellofx`. Once a GraalVM 25+ distribution and a matching C toolchain are set up, you can build a self-contained executable with:

[source,shell]
----
mvn -Pnative package -pl jfx-static-examples/example-hellofx -am
----

Note that `jfx-static-libs` can also be used standalone in case you are only interested in the metadata and need it for https://medium.com/db-one/building-javafx-app-native-image-with-graalvm-new-achievement-unlocked-c5e236ecf11d[dynamic linking]. The static archives are ignored unless the matching feature is included.


== Three Problems

Several layers have to work together to make JavaFX run as a native image. In general, there are three problems that need to be addressed:

1. *Reachability metadata*: Native image uses a closed-world assumption, so every resource, class, and method that gets accessed reflectively at runtime needs to be known at build time (e.g. `reachability-metadata.json`). The metadata consists of two separate parts: the metadata specific to the user's application, and the generic metadata for the underlying engine. The engine metadata is tied to the JavaFX version and operating system.

2. *The static binaries*: Roughly half of JavaFX is C/C++/Objective-C code (windowing, rendering, fonts, image loading, effects). A self-contained executable needs these libraries compiled and linked in as static archives. https://github.com/openjdk/jfx[jfx] already supports building the archives via `-PSTATIC_BUILD=true`, but they currently don't get published.

3. *Static integration glue*: A few things work differently under AOT and need to be bridged with glue code. For example, GraalVM's linking step requires the native symbols of all included classes to be available at link time, even if some code paths could never be reached. This is an issue when, e.g., a Windows image wrongly includes a Linux font rendering class that uses JNI and depends on several Linux-only symbols. The resulting missing symbol errors can look cryptic to Java developers and give the impression that the binaries were not compiled correctly.

=== Application Metadata

The application part of the metadata is independent of the build solutions that are the focus of this blog post, but it's by far the most common problem from a developer's perspective, so I want to cover it before the engine parts.

On the application side, most of the reflection and resource loading comes from FXML and CSS. Desktop applications load many types of files at runtime (e.g. `.css`, `.fxml`, `.png`, `.jpg`, `.ttf`) that need to be included in the native image, and the metadata also needs to cover side-effects such as importing other resources or reflectively instantiating classes (e.g. `@import`, `-fx-skin`, `fx:controller`).

The corresponding metadata lives in a `reachability-metadata.json` file that is hard to maintain manually and keep in sync. The typically recommended way to create the metadata is GraalVM's https://www.graalvm.org/latest/reference-manual/native-image/metadata/AutomaticMetadataCollection/[tracing agent], which attaches to a normal JVM run and traces all reflective accesses. That works reasonably well for a backend service with an automated test suite that hits every endpoint, but it is a major pain for GUI apps. Developers would have to click through every feature on every operating system, and redo it every time the app changes.

In practice, nearly every issue we encountered in production was due to agent data becoming stale. It got annoying enough that we created https://github.com/HebiRobotics/reachability-annotations[reachability-annotations], which let us define metadata via annotations that live next to the source of truth and can never go out of sync:

[source,java]
----
// Whenever this class is included, the resources are automatically added
@Reachable(resources = { "images/*.png" })
public class ImageLoader {}
----

We also added JavaFX-specific annotations that automatically parse `FXML/CSS` files and generate appropriate metadata for everything they reference:

[source,java]
----
@ReachableFxResources({
        "/assets/images/*.png",
        "views/**/*.fxml",
        "views/**/*.css",
})
public class MyApp extends Application {}
----

With a few annotations we can make all https://github.com/gluonhq/gluon-samples/pull/189[gluon-samples] run out of the box on all platforms without ever running an agent. Even our complex apps do not use the agent anymore outside of explorative runs. By default, all entries are conditional, so unused views do not increase the image size.

Unfortunately, there are still some third-party libraries that are notoriously hard to get running, e.g., some reflection-based parsing libraries, and they may need to be replaced with something more compatible. Note that this is not specific to JavaFX, but it remains a pain point for native images in general.

=== Engine Metadata

Unlike the application metadata, the engine metadata is constant for a specific version and operating system. Users only see a pure Java API, but internally there is a lot of native code for dealing with OS behavior and rendering pipelines, and a lot of reflection to pick appropriate implementations at runtime. Between the reflection, JNI, and resources (shaders, css files, fonts, etc.), it currently takes close to 800 metadata entries to cover the whole framework.
// TODO: verify the approximate counts (metadata entries here, annotations/files in the note below) on the final branch

Additionally, a lot of the metadata only applies to specific operating systems. Many of the platform-specific classes (e.g. `WinApplication.class`) get filtered out of the platform jars, but a few classes (e.g. platform fonts) are always available. Adding those unnecessarily bloats the native-image, and can even break the build. For example, accidentally adding the Windows DirectWrite font backend on Linux results in 65 unresolved symbols at link time even though none of those symbols are needed.

The metadata cannot be generated with an agent as it is impossible to cover all possible paths in a single application. The shaders and effects alone form a large family of generated classes, some accesses depend on the class loading order, and each run is limited to a single pipeline. Therefore, this metadata needs to be curated in some way, and ideally use wildcards to cover all shaders at once.

**Substrate** bundles JSON metadata with their downloaded fx jars (`META-INF/substrate/config/reflectionconfig.json`), and adds a custom mechanism that appends OS-specific metadata (e.g. `reflectionconfig-x86_64-linux.json`) before handing it to native-image. They also offer a `usePrismSW` flag that adds additional `-javafxsw` variants for the software pipeline. Only Substrate reads these suffixes, so the metadata does not work when using the stock `native-maven-plugin`.

**Liberica NIK** ships no JSON files at all. Instead, they heavily extended the https://github.com/oracle/graal/blob/6d71c876640c9ae7b3c131ebecc8d1834ac813c7/substratevm/src/com.oracle.svm.hosted/src/com/oracle/svm/hosted/javafx/JavaFXFeature.java[com.oracle.svm.hosted.javafx.JavaFXFeature] in the `svm.jar` and register rules directly from code. The metadata is tied to the bundled jfx version, and the conditions are generated using `Platform.includedIn` checks and triggers on specific classes.

**jfx-static-libs** ships conventional JSON files with conditions that approximate OS filtering, e.g., `isReachable(${OS}Application.class)`. This is compatible with the stock tooling, so it works out of the box with any GraalVM version. The metadata itself is currently generated using `@Reachable` annotations in my https://github.com/ennerf/jfx/tree/jfx26u-metadata[ennerf/jfx] fork and updated per release.

Missing metadata fails rather annoyingly at runtime, so we set up a verification project that executes as many code paths as possible, e.g., 2D and 3D scenes, effects, dialogs, popups, and rich text. Each scene exports screenshots that undergo automatic pixel checks and are exported for manual side-by-side verification. Beyong the synthetic tests, we also check the AtlantaFX sampler and our own internal applications like https://www.youtube.com/watch?v=E9csKYFPwaM[Scope]. === The Static Libraries

The static binaries are the most mechanical problem. Upstream OpenJFX has supported static builds via `-PSTATIC_BUILD=true` for years, but has never published the resulting archives, so everyone who wanted them had to either build them or take a vendor's patched version.

The two vendors solve this in opposite ways. Substrate downloads Gluon's own static JavaFX SDK and swaps the JavaFX jars on the class path with its own before invoking native-image. That guarantees matching jars and archives, but the JavaFX that the user compiles and tests against on the JVM is not necessarily the JavaFX that ends up in the image, and the version has to be one that Gluon has published. Note that the swap is silent, e.g., our test build declared JavaFX 21 and the resulting image reports `21-internal+11.2`. BellSoft avoids the problem entirely by bundling, i.e., there is exactly one JavaFX in the picture. The bundled modules take precedence over any `org.openjfx` jars that the build declares, which then only add dead weight to the image.

Our archives instead come directly from upstream. https://github.com/ennerf/jfx[ennerf/jfx] is a fork of `openjdk/jfx` at the release tag that adds the reachability annotations and a CI workflow. There are no functional changes to the JavaFX code, i.e., the annotations only add metadata to the jars, and the fork is two commits per release. For each release, CI builds the static SDK for `windows-x86_64`, `linux-x86_64`, `linux-aarch64`, `darwin-x86_64`, and `darwin-aarch64`. Note that the Linux builds run on the oldest supported Ubuntu LTS, because the build host's headers determine the oldest glibc the archives can link against.

`jfx-static-libs` packages every platform's archives together with the metadata into a single jar of roughly 10 MB, without any classifier. Packaging all platforms into one artifact removes the need for OS detection, Maven profiles, and per-platform classifiers, and Maven and Gradle resolve it identically. The archives of the other platforms only cost a one-time download, since no resource configuration references them and they never enter an image.

One constraint that dynamic linking hides is that the Java classes and the native archives have to come from the same JavaFX build. The JNI side of JavaFX is not a stable interface, and a mismatch shows up as an undefined symbol at link time. `jfx-static-libs` is therefore versioned by the JavaFX release it was built from and declared with the same `${javafx.version}` property as the `org.openjfx` jars. If the versions still disagree, e.g., due to a stale pin in a parent pom, the feature aborts the build with a message that names both rather than failing with a linker error. The feature itself has its own version line, since the substitutions have not had to follow a JavaFX change in years.

=== Integration Glue

Linking the archives into an image is the last problem: something has to tell native-image that the JavaFX native code is compiled into the image rather than loaded from shared libraries, and work around the places where GraalVM and a statically linked JavaFX do not fit together yet.

This is handled by `jfx-static-feature`, a GraalVM https://www.graalvm.org/sdk/javadoc/org/graalvm/nativeimage/hosted/Feature.html[Feature] that is picked up from the class path by any stock native-image. It registers the JNI package prefixes as builtin, adds the platform's archives as static JNI libraries, and names the system libraries they reference, i.e., GTK on Linux and the Cocoa frameworks on macOS, which stay dynamic (see Trade-offs). Doing this in a feature keeps the list out of every consumer's build without patching anything.

Registering the libraries as builtin means that every reachable native method gets bound at link time. Eager binding only pulls the referenced objects into the image, and it turns a missing implementation into a build error. NIK's patched native-image works the same way. Substrate instead forces the whole archives into the image on Windows and macOS (`/WHOLEARCHIVE` and `-force_load`), where the JNI methods resolve lazily at runtime, the same as on a JVM, i.e., nothing gets verified at build time.

A practical consequence of these differences is the software pipeline: a jfx-static image always contains the sw fallback, while neither vendor image currently does. Substrate's Linux desktop builds never add the sw archive to the link even with the flag enabled, and NIK's sw registrations exist in the code but never get called. Those images therefore require a qualifying GPU to start at all.

==== Removing the Need for C Stubs

The per-platform `javafx.graphics` jars already exclude most code of the other platforms, i.e., each jar only carries its own windowing and rendering pipeline. However, the font backends have slipped through: out of the 95 graphics classes that declare native methods, exactly the six font classes and the iOS image loader are also present in the other platforms' jars. Nothing reaches them on the wrong operating system by itself, but a single bad metadata entry does, e.g., agent output that was recorded on a different OS and committed to the repository. The registered classes enter the analysis, the archives contain none of their native methods, and every unresolved native method in a static JNI library becomes a link error:

[source]
----
helloworld-graal.obj : error LNK2001: unresolved external symbol
                       Java_com_sun_javafx_font_coretext_OS_CFArrayGetCount
[... 54 more unresolved CoreText symbols ...]
helloworld-graal.exe : fatal error LNK1120: 55 unresolved externals
----

These errors look like a broken toolchain rather than a wrong JSON entry. The obvious fix is a small C stub for each missing function, which would come out to dozens of stubs per platform.
// NOTE: linking and failure-mode claims verified 2026-09-09 on Windows x64 AND Linux x64
//   (hello-native-test; claude-memory/openjfx-static/verify-wrong-platform-metadata.md);
//   macOS untested. The extended @Delete stubs (CTFactory, coretext OS, OSFreetype, OSPango,
//   DWFactory, directwrite OS, dead FT_Get_Char_Index) ship with the 1.0 release.
//   Gluon nuance: lazy/whole-archive on Windows+macOS only; plain -l on Linux emits
//   references and failed there on 20 pisces symbols (their own libprism_sw.a missing from
//   the link line).

I wanted to avoid this: custom C stubs would need a matching toolchain on every platform and would have to match the JavaFX version exactly, so they would only really be safe if they were generated inside the JavaFX build itself.

Instead, the feature uses GraalVM's `@Delete` substitution to remove those classes from the analysis entirely, so their native methods are never reachable and never need to resolve. This is plain Java, independent of the JavaFX version, and requires no toolchain beyond what native-image already needs. The conditions are negations (`NotLinux`, `NotMacOS`) rather than inclusion lists, so a future iOS or Android port would fail visibly instead of silently keeping a stubbed-out backend. The deletions also cover the bad metadata from before: the same config builds cleanly with the feature, and anything that still reaches a deleted element fails with an explicit error message instead of a missing symbol. Each deletion is additionally guarded by a check that the target class actually exists, so a future upstream cleanup removes the stub instead of breaking the build.

The other routes are exposed to the same mistake in different ways. With Substrate's lazy linking on Windows and macOS, the mistake surfaces at the first call as an `UnsatisfiedLinkError` pointing at the `java.library.path`, which sends developers looking for a shared library that was never supposed to exist. NIK keeps the known font classes out of the link with hand-written per-OS wiring inside their patched native-image, which works until upstream moves. For example, JavaFX 24 added a native method to `com.sun.glass.ui.Application` whose implementation ended up in the `prism_common` archive, so a single metadata entry for that class fails the NIK build with an unresolved symbol. On Linux, where Substrate links with plain flags and does get link-time references, the same test metadata failed on twenty symbols of Gluon's own software pipeline, i.e., an archive that never makes it onto their link line. Note that none of these gaps involve wrong-OS classes. They are ordinary coverage holes, which eager linking reports at build time and lazy linking defers to the first call.

Beyond the deletions, the feature contains a small number of substitutions that work around remaining gaps between GraalVM and a statically linked JavaFX, e.g., calling the `JNI_OnLoad` initializers directly and pumping a Cocoa run loop on the first thread on macOS. Several of these are latent issues that nobody could notice on a JVM, where unused classes are never loaded and an outdated `JNI_OnLoad` version is simply accepted. Static linking removes that slack and turns them into hard errors. The appendix lists them individually.

== Trade-offs

There are a few limitations that are worth being clear about:

* *System libraries.* The image contains all of the JavaFX native code, but GTK on Linux and the Cocoa frameworks on macOS are dynamic dependencies, the same as for any native application. Any machine that can run GTK applications has everything the image needs.
* *Raspberry Pi.* JavaFX qualifies GPUs using a vendor allowlist that predates the Pi's Mesa V3D driver, so the es2 pipeline requires `-Dprism.forceGPU=true` and otherwise falls back to software rendering. The upstream fix is a one-line addition to the allowlist.
* *Image size.* A minimal application comes out at roughly 46 MB on Windows and 52 MB on Linux, i.e., in the same range as Liberica NIK and noticeably smaller than Gluon Substrate. Note that each stack links a different JavaFX version even when the poms declare the same one, so the numbers are only rough guidance:

== Appendix: The Remaining Glue

This section collects the individual workarounds inside `jfx-static-feature` for readers who run into the corresponding errors, or who want to fix the underlying issues. None of them are application specific, and most of them belong upstream, either in GraalVM or in OpenJFX:

* `System.loadLibrary` cannot load any of the static JavaFX libraries. On Windows, glass reports JNI version 1.2 from its `JNI_OnLoad`, while the spec requires 1.8 or later for statically linked libraries (an upstream bug with a one-line fix). On Linux and macOS, the `JNI_OnLoad_<lib>` symbols are hidden by the image's linker version script. The feature calls the initializers directly.
* Overloaded native methods never link, because native-image resolves builtin JNI methods by their short name, and an overloaded native only exists under its signature-mangled name on the C side. The four `directwrite.OS` overloads on Windows, and `MacTimer._start` and `coretext.OS.CFStringCreateWithCharacters` on macOS, are routed to the mangled symbols via `@CFunction` substitutions.
* On macOS, the process hangs before the first window appears. Cocoa requires the first thread of the process to be pumping a run loop while glass starts up. The `java` launcher arranges this, but a native image runs `main` on the first thread. This has been known since https://github.com/oracle/graal/issues/994[2019], and the common answer has been an external Objective-C launcher. GraalVM's `-H:+RunMainInNewThread` option moves `main` off the first thread, but does not pump a run loop, so the hang remains. The feature keeps the launcher thread and pumps `CFRunLoop` on the first thread instead, in plain Java.
* Objective-C categories are dropped from static links, which shows up as an `unrecognized selector` exception when the first window opens. `libglass.a` is linked with `-force_load` to keep them.
* The application's own `Application` subclass cannot be instantiated. GraalVM's built-in JavaFX support registers `Application` subclasses for reflection, but not the no-argument constructor that the launcher actually calls, so JavaFX native images currently fail at startup with `NoSuchMethodException: MyApp.<init>()` unless the application registers itself. The feature registers the constructor of each subclass as it becomes reachable, so unused launchers in the same jar cost nothing.

As for the rendering check mentioned in the metadata section, the same binary can be pointed at the GPU pipelines (`-Dprism.order=d3d`/`es2`/`mtl`) to verify that the hardware paths render the same image as the software pipeline. The most instructive failure was a missing effect peer that no build error or exception would have caught: the first time the check drew a `DropShadow` on the software pipeline, the snapshot came back fully transparent, because the hand-written `BoxShadow` peer was not registered while its 28 generated siblings were.
